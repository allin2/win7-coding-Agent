# 增量验收与发版工作规范

生效日期：2026-10-04。依据：ADR-0169（Accepted，负责人要求将本次经验作为后续验收规范）。
目标：更早发现真实产品问题，减少相同输入的重复检查、夹具返工和重复实机启动。
复盘事实见[流程复盘](../reports/2026-10/acceptance_workflow_retrospective_2026-10-04.md)。

## 1. 适用范围与约束

- 新任务、新验收方案按本规范设计；既有任务在不冲突处采用。已有具体授权、固定执行顺序、
  必跑矩阵、候选冻结和安全门继续有效；需要改变时在对应合同写明差异并取得适用批准。
- 本规范规定工作顺序和复用条件，不授予产品实现、远端写入、系统修改、提交、推送或发布权限。
  实现仍满足 [AGENTS.md](../../AGENTS.md) C14，兼容性与依赖仍按
  [WIN7_CONSTRAINTS.md](../WIN7_CONSTRAINTS.md)，验收覆盖仍按任务书和
  [EVALUATION.md](../EVALUATION.md)。
- 只执行与本次改动有关的条目及合同必需项。本文不是要求每次增加全套测试、新报告、审批或工具。
  信息优先写入已有任务书、矩阵和运行记录，不另建平行台账。
- **Alpha 阶段节奏（ADR-0288）**：当前处于 Alpha，以产品迭代为先。新增检查、彩排、授权、审核或工具前，
  写明它能抓住哪种现有验证抓不住的失败；写不出就不加，或列入 RC 阶段任务书。
  安全红线和证据分级保持；C14 授权按 ADR-0290 的范围机制。
- 不把旧 FAIL/UNKNOWN 改为 PASS；未知不能填零；开发机、Win10、Win7、普通用户与管理员证据分别陈述。
  Win7 物理机/VM 类型由适用任务合同决定，Win10 结果不能替代 Win7 直接证据。

## 2. 开始前形成一份简短影响记录

在已有任务或执行记录中写明以下六项；事实能查到就自行查明：

1. **交付结果**：用户可观察的新行为，以及这轮完成所需的验收范围。
2. **实际基线**：仓库、分支、HEAD、dirty/untracked、产品/原生锁和现有证据位置。
3. **改动影响**：产品、原生、打包、普通夹具、取证或环境中的哪些部分变化，影响哪些上下游。
4. **本轮检查**：每项标明直接重跑、满足条件后继承或不适用及原因；未执行单列。
5. **执行边界**：已有授权、准确目标/账户、目录、可修复范围、失败停止与重试条件。
6. **最短真实链路**：能尽早暴露本次集成问题的实际产品操作，优先于长耗时边界测试。

交付范围以需求覆盖为单位；通过断言数量、报告数量和工具调用次数不能代替完成判断。
同一依赖链存在多个已知缺陷时，在获批范围内一并修复、检查共性入口，再进入下一轮实机；
未证实的猜测不作为扩大重构或检查范围的理由。

## 3. 开发到发版的执行顺序

| 步骤 | 工作 | 进入下一步的依据 |
|---|---|---|
| 本地开发 | 按依赖顺序编译；运行受影响的单元/集成检查和合同必需静态检查 | 当前源码对应的实际消费者通过，故障反例有效 |
| 执行环境与工具准备 | 轻量核对目标身份、运行时、输入、空间；检查本轮新改夹具/取证组件 | 真实运行环境能够加载执行，记录可返回且安全收尾有效 |
| 最短真实产品链路 | 以开发包通过实际 main/preload/IPC/State/UI 和包内原生模块执行关键路径 | 用户可见结果、必要持久化及进程收尾都有直接证据 |
| 受影响回归 | 完成本次功能及共享安全/生命周期路径；未变化内容按条件继承 | 需求矩阵无遗漏，失败已定位和闭环 |
| 候选准备 | 完成适用独立复核、原生双构建/重锁、包完整性、SBOM/许可证及目标预演 | 输入、产品和验收工具稳定，候选准入门满足 |
| 正式目标验收与发版 | 冻结候选后执行当前候选的目标平台合同、报告审核和负责人裁决 | 正式 PASS 与具体候选绑定；按授权发布同一验收产物 |

原生改动的实际编译、正确性及其构建门，必须在依赖新原生工件的产品检查之前完成。
现有合同若要求双构建/重锁后才能装配开发包，仍按该顺序执行。
没有该要求的开发探针只标开发证据，不能进入正式锁或冒充候选。

涉及 Win7 专属兼容性的不确定性，应在已获批的开发探针环境尽早做最小 Win7 检查，
不等到长时间 Win10 回归完成才首次发现平台差异；这不启动前置门尚未满足的正式候选验收。
普通文档或无关模块变化不自动触发远端、GUI、截图或 Win7 检查。

### 3.1 先编译依赖，再测试消费者

- Shell/Runtime 等检查若读取 sibling `dist`，先完成其依赖构建。当前仓库可用已有
  `npm run verify:quick` 完成规定编译/静态门，再跑定向消费者测试；已成功且输入未变则不重复。
- 构建失败停止对应消费者检查；核对父进程与子进程实际使用的 Node、编译器和 PATH。
  源码新、`dist` 旧时不能据测试结果判产品回归。
- 打包从所绑定源码按生产者合同编译，不把工作区残留 `dist` 当成新包输入。
  若需隔离生成文件，采用既有获批构建路径；不靠删除用户文件或全仓恢复来获得干净状态。
- 路径、权限、持久化、编码等是被测行为时，集成测试保留真实实现；不得将 canonicalizer、
  审计或实际状态层替换为空操作后声称相关边界已经覆盖。
- 对已复现缺陷优先保留能在原实现上失败的反例，修复后验证同类实际入口；
  可逆低风险改动不添加只复述实现的测试。

### 3.2 先检查新改测试工具，再启动长流程

只检查本轮受影响的工具能力，复用已有脚本；不得为流程优化另起通用验证平台。

| 工具变化 | 应优先检查的真实条件 |
|---|---|
| 请求/脚本/Renderer 表达式 | 实际 PS5.1、Electron/Node 版本解析与调用；合法请求及关键拒绝反例 |
| 包读取/加载 | Electron 实际文件视图、ASAR 物理校验、原生 ABI 和模块加载入口 |
| 进程取证 | 短命进程、同实例/父子/Session 绑定、时钟边界、正常和失败收尾 |
| 输出与回收 | 预算内正例、超预算结构化失败；实际记录体积、传输/解析上限和原始字节回收 |
| 桌面调度 | 实际普通身份和合同 Job 条件、一次启动后的请求/失败重试/停止 |

候选内代码不按开发根、正式根或证据类别切换行为。确需切换时，正式分支须在正式执行前的彩排中实际执行过；
只在开发根跑过的彩排不证明正式分支（ADR-0288）。

构造输入、管理员 API 探针与普通桌面直接结果分别标注。
轮询遗漏、PID 当前不存在或后补成功不能补签早先未知的实例身份/退出码；
不得通过扩大时间容差、忽略未知子进程或放宽归属校验来让工具通过。

### 3.3 最短真实链路与受影响回归

后台工具的最短链路示例：普通产品启动 → 实际工作区/模式 → 启动一个进程 →
读到输出 → Stop → 核对持久化与真实清理。先满足安全前置和必要启动基线。
随后按任务覆盖数量、游标、错属、失败、释放退出和恢复；最短链路不代替完整验收。

UI 断言等待业务状态或目标元素满足条件，采用有界等待并保存失败现场；
不以盲目加长固定 sleep 代替定位，也不通过 Mock 正式退出入口来证明产品退出。
需要截图时绑定运行身份和当时操作；窗口创建或日志写出不能单独证明用户可见结果。

### 3.4 开发级运行与正式验收（ADR-0289）

当前已确认范围按 ADR-0290 使用下表区分两级运行；旧冻结候选及正式合同不改写。任务书要加回正式流程，须按 ADR-0288 决定 1 写明理由。

| 项 | 开发级运行 | 正式验收 |
|---|---|---|
| 被测产物 | 开发构建：一个提交单次构建的 ZIP，以提交号和 ZIP SHA 标识 | 冻结候选 `WIN7-NN` |
| 双干净构建与冻结 | 不做 | 每个版本一次 |
| 封存、拒绝集、签名载荷 | 不做；每次新 run UUID | 按任务书门 A 材料清单 |
| 独立审核 | 不做 | 门 A 材料一次，门 B 结果一次 |
| 负责人批准 | 版本范围授权内不逐次请示 | 门 A、门 B 逐次签发 |
| 记录 | 自动账本：输入 SHA、动作、结果 | 原始证据、覆盖矩阵、门 B 结论 |
| 结果用途 | 标 `DEV_CHANNEL`，只作诊断 | 唯一能产生 Win7 PASS 的一层 |

冻结候选须先在开发级运行中全阶段通过一次，才进入门 A。
正式执行的候选内代码与驱动字节，与该次开发级运行相同。

需求或版本范围授权写明：结果、行为边界与实际分支、本地提交、开发构建、开发级运行、模型请求与目标机时间预算、停止条件。
新增权限或系统修改、超出预算、门 A 与门 B 签发、推送与发布，仍逐次请负责人批准。

## 4. 重建、复验与证据继承选择

| 改动 | 最小有效验证与重建范围 |
|---|---|
| 文档/证据索引 | 文档、链接、差异检查；文档若改变可执行合同，另核对其影响 |
| 普通测试夹具 | 夹具检查及失败/受影响场景；安全收尾已证明且合同允许时同窗口新 revision 重试 |
| State/Core/JS/TS/UI | 重编受影响依赖、装配新包并验证包内入口；重跑相关真实集成与共享安全路径 |
| 原生源码/协议/ABI/工具链/构建参数 | 实际构建、适用双构建、PE/API/CRT、重锁及受影响产品/目标平台检查 |
| 捕获器/身份/审计/清理证明规则 | 工具实际准入及反例；重验依赖其证明的场景，不热改运行中的冻结安全组件 |
| OS/账户/Session/权限/运行时环境 | 重新直接确认相应环境条件与受影响行为；不因地址或账户名相同推定一致 |

产品 JS/State 修复不自动触发 helper 双构建。复用原生工件须确认源码、工具链、参数、
依赖、Profile、协议调用和锁均适用；协议或调用行为改变则重新分析原生影响。
新包始终直接校验自身身份、完整闭包和实际加载，不继承旧包的整体 PASS。

继承须同时满足组件字节、依赖/参数/配置、相关上下游调用行为未受影响，原报告可核验，
且当前合同允许；按原 source/工件/run/environment/user/report hash 指向来源，标
`INHERITED_EVIDENCE`。State 变化可能影响 SQLite/IPC，不能只因 Shell 源码未变就跳过集成。
无法确定影响时补最窄的相关检查，不自动回到所有历史测试。

## 5. 失败处理与停止重复循环

先保存首个结构化错误、实际加载输入及必要原始结果，再断言和汇总。

| 失败类别 | 处理与重试条件 |
|---|---|
| 编排/环境失败 | 定位连接、磁盘、身份或工具条件；只修复获批范围，满足原准入后重试；不记为产品 FAIL |
| 普通夹具断言失败 | 核对预期和合同，先保留旧结果；实际树结束且无硬门失败时，按合同用新版本和 run 重试 |
| 产品功能失败 | 在获批范围中最小修复、检查共性入口；形成新源码/包身份，再跑受影响链路 |
| 身份/完整性/安全/必需审计/未知生命周期 | 立即停止其全部依赖派发与下游 Gate；保留 FAIL/UNKNOWN，按合同处理新入口和恢复 |
| 报告或传输失败 | 保留原始文件，允许在获批范围另存解析/回收补充；不改原事实，证据未核验前不签 PASS |

同一类失败连续两轮仍未解释或闭环时，暂停该整批重试，形成一个最小复现或定向诊断，
检查共同根因和判据可实现性；其余独立且已授权工作继续。这个止损点不自动增加审批或委派。
只有原因/修复/验证出现新证据，才进入下一轮受影响实机；不以编号递增、等待变长或断言减少算进展。

正式执行（门 A 授权下的执行）失败一次即停止重试：先读回收的原始证据，把原因定位到具体代码或环境条件。
外层错误标签不等于原因；只重新生成输入、不改原因所在字节的重试不算定位。原因确认前不发起下一次正式执行，
也不请负责人确认新载荷（ADR-0288）。

修复提案先给修掉根因的最小改动和能证明它生效的最少验证。附带的防护、额外彩排或新授权单列为 RC 候选，
不与修复捆绑审批（ADR-0288）。

验收工具（候选外驱动、夹具、编排）的同一问题，连续 2 轮开发级运行未闭环时，停止加固，提交删减提案：
删哪项检查、此后不覆盖什么。负责人裁决后登记为已知限制；未经裁决不得减少断言或放宽判据（ADR-0289）。

普通失败可恢复窗口与安全硬停止必须区分；已 HALTED 的控制器不能按普通失败继续。
旧失败不会使所有未来任务永久重跑，但也不能借新结果洗掉旧未知。

## 6. 版本、授权与桌面复用

- 每次运行明确产品源码/包、原生输入锁、测试 driver、取证/调度组件、实际环境和 run ID。
  沿用既有记录格式，不因本规范强制新增协议或 Schema。
- 产品、普通夹具和安全取证分别记录变化。执行过的输入与证据不可覆盖；普通夹具修复可生成
  新不可变版本，避免无关产品重建。安全组件改变则按影响复验，不热替换原安全门。
- 复用已验证的“一次普通桌面启动，后续 SSH 固定请求与回收”能力；实际进程仍核对 SID、
  Session、完整性、提升状态和合同 Job 条件。不得把管理员/Session0 或计划任务配置当成桌面通过。
- 新合同一次明确同范围局部修复、检查、允许的新版本/运行目录规则、次数/时限与停止条件。
  合同已涵盖的普通重试不重复求批；实际源码/产物形成后在执行前绑定并核验准确哈希，不用占位哈希。
  开发级运行的哈希由执行代理在账本中自动绑定，不请负责人确认（ADR-0289）。
- 授权不能覆盖任意未来源码或系统权限。新增 API/权限/目标/实现范围、改变证明判据等仍执行
  适用评审与批准。提交、远端写入、发布各按已有用户授权和具体合同，不从流程规范推导权限。
- 目标机执行只经局域网直连。链路不达标时等待或改期，不为适配链路修改执行工具、预算或合同（ADR-0288）。
- 已用 run、主机地址、拒绝集这类登记数据放在授权绑定的数据文件中，不写进需要重钉的执行工具字节或测试。
  新设计的执行包照此执行；既有执行包在 RC 阶段调整（ADR-0288）。
- 容量在准备前检查；不足时停依赖动作。规范不授权清理历史包、数据库、候选或证据。

## 7. 正式验收和发版收口

候选冻结前，复用已有矩阵逐项确认以下条件；只补缺项，不重复已完成且输入未变的检查：

1. 当前源码、构建输出和打包输入一致；关键产品链路及适用开发/构建门完成。
2. 验收脚本在实际运行时可用，期望与产品合同一致，安全/失败收尾路径有依据。
3. 当前需求逐项关联直接检查或获准继承；故障反例与真实产品入口满足任务书。
4. 无未处理的阻断性安全/完整性/生命周期问题；非阻断限制按原合同说明，不能自行降级。
5. 目标、账户、环境、原生锁、包/manifest、证据目录及适用角色/批准已准备。

按任务冻结候选后，执行当前候选的 Win7 验收。预演次数、双构建、独立审核、门 A/B
以具体任务为准，不给所有后续任务机械增加“两次全量预演”。新建任务书默认每个版本各一次，见 §3.4（ADR-0289）。
技术检查通过不等于负责人接受。
产品或包内验收脚本需要改变时形成新候选；候选外工具改变按合同产生新版本和新证据，
不把外部脚本修订一律等同产品重建。

发版使用已验收的准确产物，校验标签/源码、发布附件和验收哈希；发布前重新构建产生新字节，
须重新分析证据适用性，不能沿用原包 PASS。保留原包、回滚位置和声明限制。
推送、发布和删除须有相应授权；正式验收完成前，未执行项继续记 `NOT_PERFORMED`。
