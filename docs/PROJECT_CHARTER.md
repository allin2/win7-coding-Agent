# PROJECT_CHARTER — 项目章程

## 1. 背景与动机

存量工业与办公环境中仍有 Windows 7 SP1 x64 机器因合规、驱动或专用软件绑定而无法升级。项目的唯一固定客户端条件是 **Windows 7 SP1 x64**；Python-only、stdlib-only、禁止 Node.js/Electron、最终仅 CLI、完全离线、禁止后台进程/插件/并发等项目级限制已由 ADR-0027 废止。

项目目标不是把旧平台伪装成现代 Windows，而是在明确的 Win7 能力边界内提供尽可能接近现代 Coding Agent 的体验：本地负责界面、工作区操作、受控执行、状态与审计；模型推理以及 Win7 无法安全承载的现代能力默认放在远程或企业内网服务。

## 2. 项目目标（最终态）

最终产品按 `docs/ARCHITECTURE.md` 的四个核心边界演进：

1. **Desktop Shell**：提供桌面任务、会话、审批、差异、终端与设置界面；CLI 保留为诊断和自动化入口，但不再是唯一产品形态。
2. **Agent Core**：管理任务状态机、上下文、Policy、权限确认、工具编排、多任务与可恢复状态。
3. **Runner**：以结构化参数执行工具和测试，强制超时、输出上限、进程树终止、工作区边界与审计；交互终端与 Agent 工具执行隔离。
4. **Gateway**：连接企业内网/远程模型与工具服务，处理鉴权、协议版本、流式事件、重试和断线恢复。
5. 提供编码感知的代码读取、搜索、补丁写入、备份、验证和回滚。
6. 支持版本化状态、事件与审计导出，故障后可恢复或安全失败。
7. 允许通过后续任务书引入 Skills、Hooks、MCP/插件、多 Agent、后台服务和并发调度；这些能力必须逐项设计信任边界与资源预算。
8. 对 Win7 缺失的 ConPTY、现代浏览器沙箱、WSL2、Docker Desktop、Windows Sandbox 等能力，提供显式降级、替代适配器或远程化方案。

## 3. 当前范围与授权边界

Phase 1/2 保持历史冻结合同；ADR-0028~0035 已由 ADR-0036 条件接受。Phase 3–7
任务书已获实现授权，非终端/containment 部分可理论先行；跨阶段整合由
`INTEGRATION_01_ROBUSTNESS_HARDENING` 承载。上述授权不等于阶段完成，Win7 Spike、
企业环境与端到端验收仍是硬门槛。

### 当前已授权

- 阶段 0：维护文档、约束与 ADR。
- 阶段 1：按 `docs/tasks/PHASE_01_CAPABILITY_PROBE.md` 实现历史冻结的 CPython 3.8.10 标准库 Capability Probe。
- 阶段 2：仅在指定分支和允许路径内，按 `docs/tasks/PHASE_02_READONLY_CODE_ANALYSIS.md` 实现 Mock/Replay 驱动、目标工作区只读的代码分析 Agent。
- 阶段 3–7：按各自任务书实现理论基线；整合、健壮性加固和文档对账限于
  `docs/tasks/INTEGRATION_01_ROBUSTNESS_HARDENING.md` 白名单。
- SPIKE_01~04：按各自任务书采集 Win7 实机 Go/No-Go 证据。

### 当前未授权

- Phase 1/2 不接入真实模型、不修改目标用户代码；其合同不被新客户端追溯扩大。
- SPIKE_02 通过前不定稿真实 Runner containment 或交互终端，不用 `taskkill` 冒充隔离。
- v1 不实现 full-access 本地等价、插件宿主或多 Agent（ADR-0030/0034/0035）。
- 未列入获批任务书白名单的实现仍未授权。

后续新组件和范围扩展仍必须先有独立 `APPROVED_FOR_IMPLEMENTATION` 任务书，并声明允许
路径、精确版本、交付闭包与 Win7 验收矩阵（AGENTS.md C14）。

## 5. 成功标准

### 当前阶段

- Phase 1/2 的历史冻结合同、分支、路径白名单和 Win7 验收门槛保持不变。
- 项目级文档不再把 Python 3.8、标准库、CLI 或完全离线误写为最终产品唯一方案。
- 所有新增实现仍可追溯到一个已批准任务书和一条明确的运行时/依赖 Profile。
- Phase 3–7 整合基线可在开发机重复构建测试，但明确标注尚未通过 Win7 实机门槛。

### 项目级最终态

- 声明支持的每个客户端 Profile 均在 Win7 SP1 x64 实机上完成安装、启动、升级/回滚、核心工作流与异常恢复验证。
- 桌面交互、Agent Core、Runner 和 Gateway 的边界清晰；模型不能绕过 Policy、审批、工作区和审计直接执行。
- 中文/空格路径、UTF-8/CP936/CRLF、网络中断、超时、超量输出与进程树终止均有可重复测试。
- 自包含离线包、企业内网安装或受控更新至少有一种被任务书选定并验收；项目不强制所有部署都完全离线。
- Win7 不具备的能力在 UI、协议和日志中明确标识，不静默降级为不安全行为。

## 6. 关键风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| Win7 与候选运行时均已停止主流支持 | 漏洞无法通过常规升级及时修复 | 固定版本、缩小本地攻击面、企业网络隔离、来源/哈希/SBOM、补丁与退役策略 |
| Electron 22 等兼容候选内含旧 Chromium | 渲染不可信网页会扩大攻击面 | UI 仅加载受控本地内容；隔离 Renderer；外部网页与 Browser Use 远程化 |
| Win7 补丁、TLS、CA 状态不一致 | 安装、鉴权或 HTTPS 失败 | Profile 声明所需补丁、协议与 CA；安装前探测；提供可诊断错误和回滚 |
| Win7 无 ConPTY，Job Object 不支持嵌套 | 终端体验与进程树控制受限 | 交互终端候选采用 winpty；无法可靠 containment 时拒绝/远程执行高风险命令，`taskkill` 仅作低风险兼容回收 |
| 第三方或原生依赖缺少 Win7 构建 | 干净机器无法启动 | 锁定架构与版本，交付完整依赖闭包，在干净 Win7 上安装/加载测试 |
| Git/终端通过间接执行或控制序列旁路 | 未经批准的进程、网络、剪贴板或输入注入 | 专用 Git Profile、隔离配置/环境；用户终端 stdin 与模型隔离，限制 VT/OSC |
| 桌面 UI、Runner 与远程服务权限边界模糊 | 模型或页面可越权执行 | 进程隔离、最小 IPC、Policy/Broker、显式审批和不可旁路审计 |
| 网络或内网服务不稳定 | 任务中断、状态不一致 | 版本化事件、幂等请求、断线恢复、离线可读状态和明确失败语义 |

## 7. 交付原则

- 每个任务书必须选择并声明交付模式：自包含离线包、企业内网安装或受控更新。
- 交付清单必须包含精确 OS/补丁、运行时与架构、依赖闭包、入口、工作目录、可写目录、网络目标、完整性校验、升级与回滚步骤。
- 默认优先普通用户权限与可移植目录；注册表、服务、管理员权限或后台自启动不是全局禁令，但只有在任务书、Policy 和用户确认共同授权后才可采用。
- Capability Probe 应成为安装前检查的一部分；“现代开发机通过”不能替代 Win7 实机验收。
