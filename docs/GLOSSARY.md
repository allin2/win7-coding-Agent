# 术语表

依据：ADR-0190。本表规定状态词与流程名词的含义和写法，**不新增、不改写任何既有状态值或 ADR 语义**；
与 ADR、任务书正文冲突时以正文为准，并修正本表。新写或修改的段落按本表用词；历史文档不回改。

用法：一个词只表示一件事，一件事只用一个词。表中“不得混用”列给出常见误用。

## 1. 证据层级

结论必须标明来自哪一层。下层结论不得替代上层（AGENTS.md §5、§6）。

| 写法 | 含义 | 不得混用 |
|---|---|---|
| 开发机 | macOS 或其他非目标环境上的构建、单元/集成检查、Demo | 不得写成“已验证”“已通过”而不加层级 |
| Win10 验收机 | Win10 上的构建或产品链路检查 | 不得替代 Win7 直接证据 |
| Win7 实机 | Win7 SP1 x64 目标机上对冻结候选的执行 | 只有这一层能产生 Win7 PASS |
| `DEV_CHANNEL` | 开发级运行的结果，ADR-0254、ADR-0289 | 只作诊断；不得写成 Win7 PASS，不进覆盖矩阵和门 B |
| `SURROGATE` | 替代条件下的证据（Mock、缩短压测、替代介质等），ADR-0065 | 不是正式证据 |
| `INHERITED_EVIDENCE` / 继承证据 | 未受影响的能力按精确哈希沿用旧候选证据，ADR-0112、ADR-0169 | 不得写成当前候选直接 PASS |
| 演示 / Demo | 用真实渲染代码加桩数据，供负责人确认方向 | 不是验收证据 |
| 解说材料 | 为便于理解而生成的 HTML 页或图，见 [OUTPUT_STYLE.md](OUTPUT_STYLE.md) §3 | 不是事实来源，也不是证据 |

## 2. 单项结果

| 写法 | 含义 | 不得混用 |
|---|---|---|
| `PASS` | 按合同判据执行且满足 | 不加层级和候选时不得单独出现在结论句 |
| `FAIL` | 按合同判据执行且不满足 | 不得事后改判为 PASS |
| `UNKNOWN` | 已执行但无法判定（如证据缺失、身份无法绑定） | 不得填零，不得补签为 PASS |
| `NOT_PERFORMED` | 未执行；可加后缀写原因，如 `NOT_PERFORMED_EXTERNAL_ENV_UNAVAILABLE` | 不得写“基本通过”“预计通过” |
| `NOT_VERIFIED` | 执行范围内没有覆盖到该项 | 与 `NOT_PERFORMED` 的区别：整体执行了，此项未覆盖 |
| `PRODUCT_UNREACHABLE` | 产品在目标条件下无法进入该分支（如 ≤799px） | 通常与 `NOT_VERIFIED` 并列使用 |
| `BLOCKED` | 前置条件未满足，不能开始 | 不是 FAIL |
| `N/A` | 该项不适用于此任务类型 | 不得用来隐藏未执行项 |
| 已知限制 | 随结论一同签发、明确未覆盖或不保证的范围 | 不得省略后只写 PASS |
| fail-closed | 条件不满足时拒绝执行或保持关闭 | 不得写成“降级继续” |

## 3. 任务书状态（`Status` 字段）

任务索引另分为“当前工作与待批准任务”“已关闭任务”“历史合同与保留事项”（ADR-0192）。
分区不新增或改写 Status 值。只有当前分区中的批准任务可进入 C14 分支、白名单和 Gate 判定。
历史分区保留原批准及未关闭合同义务，不授权新实施；已关闭分区只收录 COMPLETE。

| 写法 | 含义 |
|---|---|
| `DRAFT_READY_FOR_REVIEW` | 草稿完成，等待负责人审阅；不授权实现 |
| `APPROVED_FOR_IMPLEMENTATION` | 负责人批准；只在任务书允许路径和分支内授权实现（AGENTS.md C14） |
| `COMPLETE` | 任务合同全部关闭 |
| Superseded | 被新任务或 ADR 取代，见 [tasks/README.md](tasks/README.md) 生命周期目录 |

## 4. 任务进度与结论（`Phase-Gate`、`Win7-Validation` 字段）

具体值带任务号或候选号，按下列模式读：

| 模式 | 含义 |
|---|---|
| `<任务>_DESIGN_PENDING_APPROVAL` | 设计已写，等待批准 |
| `<任务>_IMPLEMENTATION_AUTHORIZED` | 已授权实现，尚无验证结论 |
| `<任务>_DEVELOPER_VERIFIED` | 开发机检查通过；不含 Win10/Win7 结论 |
| `<任务>_<候选>_..._PASS` | 该候选的 Win7 实机验收经门 B 签发通过 |
| `..._PASS_WITH_KNOWN_LIMITS` | 同上，并附已知限制 |
| `..._PASS_EQUIVALENCE` | 按负责人批准的等效口径签发（如可达响应式状态等效） |
| `..._VALIDATION_KIT_DEFECT_NOT_PASS` | 验收套件自身缺陷导致不通过；不是产品缺陷结论 |
| `..._G2_FAILED` 等 | 在指定阶段（G1/G2/G3）失败 |
| `FIX_BEFORE_ALPHA` | 发现须修复的问题，该候选永久不能成为 Alpha |
| `GO_FOR_ALPHA` | 可作为内部 Alpha 的裁决；不是 RC |
| `RC_PASS` | 发布候选通过；当前唯一 RC 为 A7 |

## 5. ADR 状态

| 写法 | 含义 |
|---|---|
| Proposed | 提案，未批准，不构成实现依据 |
| Accepted | 已批准；正文不得改写，只能被新 ADR 取代 |
| Superseded by ADR-NNNN | 已被取代；正文保留 |

## 6. 流程名词

| 写法 | 含义 | 不得混用 |
|---|---|---|
| 负责人 | 项目所有者；唯一的批准、签发、裁决来源 | 不得写“用户”指代负责人裁决 |
| 执行代理 | 执行实现或验收步骤的 Agent | 不得兼任同一轮的独立审核 |
| 独立审核 | 未参与执行的一方核对原始证据 | |
| 候选 | 绑定源码提交、ZIP 哈希和输入锁的待验收产物 | 不得用“版本”“包”泛指 |
| `WIN7-NN` | 候选编号；首次出现时附一句说明，如“WIN7-42（第一批可靠性候选）” | |
| 冻结 | 候选身份固定，之后不得改字节 | |
| 换发 | 用新源码生成新编号候选；旧候选和证据保留 | 不得复用失败候选改判 |
| 开发构建 | 从一个提交单次构建的 ZIP，以提交号和 ZIP SHA 标识 | 不是候选；不分配 `WIN7-NN` |
| 开发级运行 | 在开发通道或其后继环境，对开发构建或候选的执行 | 不得写成正式执行 |
| 预演 | 冻结候选进入门 A 前的全阶段开发级运行；结果不签结论 | |
| 门 A | 负责人签发正式执行授权，绑定候选、目标机和 run-id | 任务批准不代替门 A |
| 门 B | 负责人审核执行结果后签发结论 | 技术检查通过不等于门 B |
| 版本范围授权 | 负责人每个版本签发一次的范围、预算与停止条件 | 不代替门 A、门 B；不扩大 C14 |
| 双构建 | 两次独立干净构建，产物逐字节一致 | |
