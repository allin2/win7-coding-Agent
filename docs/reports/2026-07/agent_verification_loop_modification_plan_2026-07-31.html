Target architecture

目标数据流

1. Task Contract用户任务、任务书与项目配置形成不可变 TaskAcceptance；模型提议只可追加为 proposal。
→
2. Gate Planner按“任务显式 > 项目声明 > 自动探测”解析 GatePlan，记录来源、信任级别和摘要。
→
3. Pipeline按成本排序执行 Gate；命令经 Runner，diff 经 Git Adapter；每步生成 GateResult。
→
4. Completion全部硬门通过生成 EvidenceBundle v2 并完成；失败则生成受保护反馈。
失败且预算尚存：VERIFYING → EXECUTING → 模型读取 verification.feedback → 修复 → 再次 VERIFYING
验证反馈应投影为 受保护的 system/harness 消息，不能伪造为普通 ToolResult。实际验证命令不是模型声明的 tool call，伪造 ToolResult 会破坏 ADR-0039 的 tool call/result 配对合同。

Architectural decisions

ADR-0051 应冻结的九项决策

1

可信验收标准不由模型控制

RuntimeRequest 新增不可变 TaskAcceptance。来源为用户/任务/项目配置的检查具有阻塞权；模型只能提交 proposedChecks，不得删除、改名或降级可信检查。

2

任务类型决定 Diff 语义

expectedMutation 使用 none | required | optional。只读分析允许空 diff；写任务必须出现相对会话基线的新改动；可选修改任务由其他验收条件裁决。

3

验证失败是可恢复状态，不是第一次就终局

新增 verification_repair_requested：VERIFYING → EXECUTING。只有通过、取消、预算耗尽、环境硬阻断或同 Gate 三连败才结束 Turn。

4

所有验证命令仍是受控执行

Gate Provider 只接收结构化 VerificationCommandExecutorPort；产品装配必须映射到 Runner V2。禁止 child_process、shell 字符串和从测试名称拼接命令。

5

Git Session Guard 是 Diff 权威入口

Git 可用时复用 ADR-0048 的干净 HEAD baseline。Diff Gate 通过结构化 ChangeSet 读取状态，不在 Core 中解析任意 Git 输出。Git 缺失时只读 Agent 可继续，写任务的 repo-wide Diff Gate 返回 unavailable 并阻止完成。

6

证据必须绑定执行事实

EvidenceBundle v2 绑定 acceptance digest、baseline digest、GatePlan digest、Runner receipt、退出码、输出 SHA-256、完整/截断状态与环境 fingerprint。自由文本 source 不再能单独形成 passed。

7

预算采用 Turn 总预算 + Verification 子预算

验证墙钟时间计入 maxWallMs；修复模型调用继续消耗 Step/Token。新增 VerificationBudget 限制总 attempts、命令数、累计输出和同 Gate 连败，默认连败上限为 3。

8

验证历史进入事件事实与 Checkpoint v3

新增 verification 生命周期事件；Checkpoint v3 保存 acceptance/baseline 摘要、失败计数与 attempt 引用。旧 v2 不得静默恢复为更弱的完成合同。

9

硬证据优先于模型意见

编译、测试、Policy、Diff 机械规则具有硬阻塞权。未来 Reviewer 仅提供软证据；不能覆盖硬失败，高风险意见触发 ASK 或用户裁决。

Core contracts

建议的 Schema 与接口形状

TaskAcceptance

interface TaskAcceptance {
  schemaVersion: '1.0';
  taskType: 'analysis' | 'change' | 'bugfix';
  expectedMutation: 'none' | 'required' | 'optional';
  allowedPaths: string[];
  expectedMaxChangedFiles?: number;
  checks: AcceptanceCheck[];
  baselinePolicy: {
    requireCleanGit: boolean;
    testBaseline: 'none' | 'targeted' | 'full';
    cacheMode: 'reuse' | 'declared_clean';
  };
  digestSha256: string;
}

GateResult

interface GateResult {
  schemaVersion: '1.0';
  attemptId: string;
  gateId: string;
  kind: GateKind;
  status: 'passed' | 'failed' | 'unavailable'
        | 'cancelled' | 'skipped';
  hard: boolean;
  commandReceipt?: RunnerReceipt;
  baselineSha256: string;
  startedAt: string;
  finishedAt: string;
  complete: boolean;
  summary: string;
  outputSha256?: string;
}

type GateAuthority =

Pipeline design

Gate 顺序与裁决规则

顺序Gate执行者硬通过条件失败行为
0Contract / BaselineCore + GitSessionGuard可信 acceptance 非空；写任务有适用 baseline配置缺失 ASK；安全基线缺失 unavailable
1Syntax / CompileRunner command alias正常退出 0，输出完整或明确可接受截断短路，反馈首个错误
2Lint / Format checkRunner command alias声明为 hard 时退出 0hard 阻塞；advisory 记录
3Type checkRunner command alias退出 0短路并反馈
4Targeted testsRunner command alias目标测试满足 red/green 或当前通过短路；不运行全量
5Full regressionRunner command alias无 baseline pass→current fail反馈新增回归，区分存量失败
6Diff mechanicalGit Adapter / ChangeSet port变更存在性、路径、数量、敏感文件规则满足硬拒绝或 ASK；不让模型自行解释
7Task acceptanceAcceptance evaluators所有可信 checks 完成且 passed反馈缺失项；预算内继续
Diff 规则不能机械照抄示例：测试文件变化并不总是作弊，因为 bugfix 正常需要新增回归测试。建议规则为：删除断言、修改既有期望、触碰 lock/config 属于 ASK 或 hard fail，除非 TaskAcceptance 明确授权；新增测试通常允许，但仍计入范围和文件数。

State and feedback semantics

状态机与失败反馈

模型最终响应（无 tool calls）
  → EXECUTING --execution_complete→ VERIFYING
  → run Gate Pipeline
      ├─ all hard gates passed
      │    → verification_passed → COMPLETED
      ├─ failed + retryable + budget remains + same gate < 3
      │    → emit verification.feedback
      │    → verification_repair_requested → EXECUTING
      │    → next model Step
      ├─ same gate failed 3 times
      │    → verification_exhausted → FAILED
      │    → TurnOutcome.STUCK + VERIFICATION_STUCK
      ├─ budget exhausted
      │    → existing budget finalization path
      └─ cancelled / cleanup unknown
           → CANCELLED or fail-closed CANCELLATION_FAILED

给模型的反馈必须包含

  • 失败 gateId、kind、attempt 次数。
  • 结构化状态与退出码。
  • 有界 stdout/stderr 摘要和完整 SHA。
  • 与上次失败的差异摘要。
  • 剩余预算和不可修改的验收条件。

反馈必须排除

  • 凭据、完整环境变量或未授权源码。
  • 未经转义的控制序列。
  • 让模型“忽略 Gate”的指令通道。
  • 伪造 toolCallId 的 ToolResult。
  • 被截断却标为 complete 的输出。

Risk controls

主要风险与缓解

架构风险

  • Runtime 继续膨胀：Pipeline/feedback/resolver 拆为独立纯模块，Runtime 只编排。
  • Checkpoint 兼容：明确 v3，不做静默字段补全。
  • 事件双重真相：attempt/bundle 是事实，模型消息由 feedback 事件投影。
  • Diff 假阳性：测试/lock/config 用声明+ASK，不用一刀切。

安全与平台风险

  • 验证命令旁路：静态扫描 Verifier/Core 禁止 child_process。
  • 恶意测试输出：字节上限、脱敏、控制序列处理、摘要投影。
  • 脏工作区：沿用 ADR-0048，写会话先要求用户处理既有改动。
  • Win7 能力未证实：Unavailable executor 保持生产默认，Mock 只证明合同。

Definition of done

本修改计划的完成标准

  1. ADR-0051 与任务书 §19 已批准，状态、路径、协议和延期边界无冲突。
  2. 审计矩阵中的 VC-03、04、05、06、07、08、09、10、12、13、18 在开发机合同层关闭；VC-14/15/16/17 按 M5 关闭。
  3. 模型无法通过空 acceptance、自报 passed、空 diff、删测试或缩小检查范围获得 COMPLETED。
  4. 验证失败可在同一 Turn 内回到模型；三连败、预算、取消和 EventSink 故障均有确定结局。
  5. Core、State、Git Adapter 的定向测试和根级 lint/build/test 通过，测试总数由机器生成。
  6. 新增静态门确认 Core/Verifier/Git Adapter 没有未授权进程入口。
  7. 创建版本化开发机验收记录，包含工作区 baseline digest、命令、退出码和证据摘要。
  8. 最终状态仍标记 Win7-Validation: NOT_PERFORMED；真实 Runner、MinGit、SQLite 与 Win7 产品 E2E 保持 Blocked。
不得把 M1–M5 的 Mock/现代开发机通过写成产品完成。它们只关闭 Agent Harness 的逻辑合同；真实命令验证仍要等待 SPIKE_02/03、精确工件 Profile 和 Win7 实机证据。
