结论

历史快照说明（2026-07-31）：本报告记录的是 ADR-0044 实施前基线。 其中 P0 投影、内容摘要、protected 预算、工具观察等结论已被后续实现取代； 当前状态请以修改计划的“当前实现状态（2026-07-31）”表和自动化测试为准。

阻断级发现

P0-1 · 上下文预算不是模型调用的强制边界

Runtime 构建了 builtContext.items，但模型输入只收到 Manifest， 同时仍收到包含全部原始 contextItems 的 RuntimeRequest。 选择后的条目内容没有成为唯一允许的模型投影，适配器可无意或有意绕过预算。

证据：runtime.ts 第 33–41、304–309、1014–1023 行。

P0-2 · Context digest 未绑定内容

Manifest 条目只记录字符数、估算 token、优先级等元数据；摘要没有内容哈希。 同长度内容变化不会改变 digestSha256。实测将 ALLOW 改为 DENY! 后摘要仍相同。

证据：context-manager.ts 第 24–30、96–110、121–127 行；复现输出 same_length_content_change_same_digest=true。

P0-3 · 硬性指令可被普通预算淘汰

instruction 只是普通 kind，没有“不可删除 / 必须保留 / 来源所有者” 语义。选择器按调用方给定的 priority 排序，达到条目、token 或字符上限后即可省略指令。 这不符合“Harness 控边界，约束来源方才可删除”的要求。

证据：context-manager.ts 第 3–15、70–94 行。

P1-1 · 工具结果无限追加到模型历史

Core 将整个 ToolExecutionResult JSON 序列化进消息；没有结果大小上限、 总命中数、截断原因、分页指针或陈旧输出折叠。长任务会持续扩大输入并稀释关键约束。

证据：runtime.ts 第 1209–1221 行。

CE-06 以 Agentic grep/read/list 为主；search 限条数并报总量，read 分页带行号，list 默认浅层。 部分满足 Phase 2 独立分支具备有界 list/read/range/search 与截断原因；当前 Node Core 只有 ToolSpec/Executor 注入边界。 Phase 2 资产未装配进当前整合 Runtime；list 仍可到 2000 项，search 未报告完整总命中数。需要 Node 生产工具合同与集成测试。
CE-07 已消费的大块工具输出可在投影层折叠为可恢复引用，而不是一直留在历史中。 缺失 State 有 compaction.applied 事件及覆盖 DAG 的协议雏形。 没有 stale 判定、输出引用、重新读取入口或投影替换；当前投影仍返回全部消息。实现可逆 fold，并验证原始事件保留。
CE-08 提供工作记忆：目标、硬约束、计划、当前步、关键发现；通过 update_plan 更新并始终注入窗口尾部。 缺失 AgentContext 仅持有 session/task/state/capability；RuntimePlan.summary 是单步模型响应。 没有 WorkingMemory schema、更新工具、尾部投影或 recitation。实现模型可更新区与 Harness 保护区分离。
CE-09 模型不得删除来自 system/user/policy 的硬约束；只有约束来源方或 Harness 可撤销。 缺失 没有约束 owner、provenance、revision 或删除权限模型。 将硬约束建模为 append-only、带来源和状态的记录；模型只能提议变更，不能直接删除或覆盖。
CE-10 KV Cache 友好：固定系统前缀和工具顺序、历史只追加、压缩按水位批量进行。 部分满足 ToolRegistry.list() 按名称排序；Runtime 消息追加；State 原始事实保留并追加压缩事件。 未冻结系统前缀；Gateway 保留调用方工具顺序；ContextManager 每轮按 priority/id 重排；无缓存命中指标和批量压缩触发器。
CE-11 审计初始上下文，删除可按需读取的信息，并对典型任务比较删减前后 token 消耗。 缺失 Runtime 记录模型报告的 token 总量，Performance Budget 没有上下文 token 指标。 缺基准场景、原始 prompt 快照、输入 token/缓存 token 分项和前后对照报告。
CE-12 运行至少 20 步任务，证明计划持续更新且目标/硬约束不漂移。 缺失 默认 Turn 上限 40 Step；现有 Runtime 测试覆盖预算与循环，但没有 20+ Step 工作记忆场景。 增加确定性 20–30 Step fixture，逐步断言尾部工作记忆、约束摘要和计划 revision。

已有资产，可保留并扩展

  • 有界选择基础： ContextManager 已有确定性排序、三类预算、省略原因和版本化 Manifest。
  • 长循环护栏： loop-control.ts 已有 Step/Token/墙钟/工具调用预算、预算收尾与重复调用检测。
  • 追加式历史： runtime.ts 能把工具结果配对后反馈给下一次模型 Step。
  • 可追溯压缩协议雏形： event-protocol.ts 保留原始事实，并以 compaction 事件表达覆盖关系。
  • 旧线输出治理经验： phase/02-readonly-agent 已实现有界 read/search/list， 可按 Phase 2 迁移纪律选择性重构，不能整体合并。

建议修复顺序

  1. P0：建立不可绕过的 Context Projection。 模型端口只接收已选择、已排序的最终消息与固定 ToolSpec，不再接收含原始 contextItems 的 RuntimeRequest；Manifest 每项加入 content SHA-256， 整体 digest 绑定实际内容、顺序和工具 schema。
  2. P0：引入受保护的上下文分区。 system/user/policy constraints 必须保留；history/tool outputs 才能裁剪。 工作记忆拆成 Harness-owned constraints 与 model-owned plan/findings。
  3. P1：实现 Bootstrap + AGENTS 分层。 初始上下文只装载环境、规则和任务；AGENTS 从 root 到 cwd，带 scope、来源、内容哈希和顺序测试。
  4. P1：实现输出治理和可逆折叠。 Node 工具统一返回 total/returned/truncated/reason/cursor；大输出消费后折叠为文件或事件引用。
  5. P1：实现工作记忆与复诵。 update_plan 只能更新计划和发现；尾部注入当前目标、不可变约束、当前步骤和证据摘要。
  6. P2：固定前缀和压缩策略。 工具 schema 稳定排序，系统前缀版本化，历史追加；达到 75% 水位后一次性压缩， 保留至少 20% 输出/压缩余量。
  7. P2：补齐量化验收。 加入典型任务 token 前后对照、缓存命中率，以及 20+ Step 无漂移测试。

作业第 4 题的裁决：Harness 不应允许模型删除硬约束。约束来自 system、用户或 Policy， 只有同一来源或更高优先级的控制面可撤销；模型最多提交“建议变更”，并由 Harness 记录为新 revision。
