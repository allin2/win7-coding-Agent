Agent 验证闭环：已有“完成门”，尚未形成“修复循环”

以《第 6 讲：验证闭环》为评审基线，对照当前整合分支的任务书、ADR、Core Runtime、Verification Gate、Runner、Git Adapter 与自动化测试。

分支 codex/integrated-robustness 工作区：脏，含大量既有未提交改动 Win7：NOT_PERFORMED 审计模式：只读源码；仅新增本报告

Executive outcome

结论：部分闭环，不满足参考材料定义的 Verification Pipeline

当前 Core 能阻止 EXECUTING → COMPLETED 直达，并要求非空、完整、通过的证据包。这是正确且重要的底座。

但验证失败后，Runtime 会立即进入 FAILED 并结束 Turn，不会把失败证据回送模型继续修复。此外，仓库中没有生产级 RuntimeVerificationProvider、没有任务/AGENTS/自动探测的命令解析、没有 Diff Gate、三连败终止、红绿测试或会话测试基线。

因此当前能力应准确描述为：“一次性完成证据门”，而不是“可自修复的验证闭环”。

完成态拦截已实现：只能从 VERIFYING 通过后完成
证据结构部分实现：有摘要包，但真实性绑定不足
可执行流水线缺失：没有生产 Gate 编排与命令解析
失败自修复偏离：失败直接终止，不回到模型

Highest-risk findings

关键发现

P0 · Divergent behavior

验证失败直接结束 Turn

src/core/src/runtime.ts:823 在证据包失败后执行 verification_failed 并返回 TurnOutcome.FAILED；src/core/src/state-machine.ts:70 只允许 VERIFYING 进入 COMPLETED、FAILED 或 CANCELLED。

对应测试 src/core/tests/runtime.test.ts:455 明确锁定“验证失败即 FAILED”。这与“失败详情回给模型，Loop 继续”正面冲突。

P0 · Missing production path

Verifier 只有接口和测试 Mock

RuntimeVerificationProvider.collect() 是注入接口；源码搜索未发现生产实现。现有 Runtime 测试用 mock verifier 按模型声明的 checkId 直接合成 passed/failed。

根级 scripts/verify_integration.mjs 是开发者验证入口，不接入 Agent Runtime，也不能替代目标工作区的 Gate Pipeline。

P0 · Trust inversion

验收要求由模型响应提供，而非任务合同提供

RuntimePlan.verificationRequirements 来自每次模型输出，并在 runtime.ts:769 累积。RuntimeRequest 没有可信的任务级 acceptance 字段。

模型既执行任务又定义完成标准，会重现参考材料指出的同源偏差。最终 Gate 只能证明“模型声明的检查有一条 passed 证据”，不能证明“用户任务已验收”。

P0 · Evidence authenticity

EvidenceBundle 可复算，但不等于证据可信

VerificationGate 只核对 checkId、status、complete 和数量。source、summary、timestamp 与 details 没有格式、当前 Run、命令结果、工作区基线或输出摘要绑定。

SHA-256 只证明 JSON 内容未在摘要后变化，不证明“测试真的执行过”或“针对的是当前 diff”。

P1 · Missing gate

没有任务感知的 Diff Gate

Workspace 已能生成内容 preview，Git Adapter 也有隔离的 diff 命令，但没有任何代码把它们接到 Verification Gate。

当前系统不能拦截“应修改却 diff 为空”、越出声明文件范围、删除测试断言或未授权配置/锁文件变更。

P1 · Missing control plane

验证命令来源与 Policy 尚未定义

未实现“任务显式指定 > AGENTS.md > 自动探测”的解析与来源记录。通用 terminal.exec 当前按 ADR-0047 fail-closed；真实 Runner 又因 SPIKE_02 未通过而不可用。

这能避免不安全执行，但也意味着生产 Agent 目前无法运行编译/测试 Gate。后续必须走专用命令 Profile、Policy、Runner 与审计，不能从 Verifier 旁路启动进程。

P1 · Missing loop guard

没有同 Gate 三连败与对比摘要

现有 LoopDetector 只检测连续三次相同工具名+参数；验证 Gate 没有 attempt 计数、失败签名、连续失败比较或专用终止原因。

P1 · Environment confidence

没有 pre-change 测试基线、红绿证明或缓存语义

审批基线能绑定写请求，但不等于验证环境基线。当前没有 FAIL_TO_PASS / PASS_TO_PASS、flaky 基线、干净构建标记或会话启动时的工作区/残留进程检查。

本次审计时工作区本身已有大量改动，正好说明“只看最终绿色”无法区分本轮回归与存量状态。

Recommended delivery sequence

最小可交付修复顺序

1

先冻结合同：ADR-0048 + 当前任务书增补

这是状态机、证据 Schema、安全执行与任务协议的关键设计变更，必须按项目规则新增 ADR。定义 TaskAcceptance、GatePlan、GateResult、VerificationAttempt 与 EvidenceBundle v2；明确可信来源优先级和 expectedMutation。

2

接通最小三门闭环

先实现参考作业的三门：语法/类型检查 → 相关测试 → 任务感知 Diff Gate。验证失败时记录 verification.bundle，转回 EXECUTING，把失败作为受保护 system 消息送入下一 Step。第三次同 Gate 失败才终止。

3

再接安全命令解析与全量回归

实现“任务 > AGENTS.md > 自动探测”，只解析为版本化命令别名和结构化 argv；全部通过 Policy、审批、Runner、超时、输出上限和 Git Adapter。真实执行仍受 SPIKE_02/03 与 Win7 门禁约束，开发机可先用显式测试装配验证合同。

4

最后提升环境可信度

增加 Turn 起点 baseline、bugfix 红绿证据、FAIL_TO_PASS/PASS_TO_PASS、flaky 标记和 cacheMode。验收记录由程序生成到 docs/acceptance/，绑定 Git commit（或 dirty baseline digest）、Profile、命令与原始结果摘要。

Acceptance checks for the fix

建议新增的不可绕过测试

  1. 模型第一次只输出“完成”且任务要求写入：Diff Gate 拒绝，Runtime 不返回 COMPLETED，失败进入下一模型 Step。
  2. 第一次相关测试失败、模型调用编辑工具、第二次通过：同一 Turn 最终 COMPLETED，usage 包含两次 verification attempts。
  3. 同一 Gate 连续三次失败：终态 FAILED 或 STUCK，结果包含三次 bundle digest 和差异摘要。
  4. 最终模型把 verificationRequirements 改成更弱条件：可信 TaskAcceptance 不被删除或覆盖。
  5. 伪造 status=passed 但缺少 Runner receipt / baseline digest：EvidenceBundle v2 拒绝。
  6. 任务声明只改 src/auth.ts，实际改测试断言或 .env：Diff Gate 拒绝或 ASK；未经裁决不得继续。
  7. 自动探测出 npm test：第一次需 ASK；批准后只允许精确 alias/argv，模型不能替换成 shell 字符串。
  8. baseline 中已有失败测试：最终仍失败不算新回归；baseline 绿而最终红必须阻止完成。
  9. 缓存产物导致假绿 fixture：cacheMode=clean 的受控命令能识别；清理命令未批准时明确 unavailable，不伪造 pass。
  10. Verifier 取消/超时：Runner 结果完整、无进程树残留才可安全结束；清理未知时 fail-closed。

Reviewer conflict rule

Reviewer 与主 Agent 冲突时听谁的

两者都不是最终权威。建议采用固定证据效力顺序：

编译器 / 确定性测试 / Policy / 路径与 Diff 机械规则
  > 可复算的运行结果与环境证据
  > 独立 Reviewer 的语义意见
  > 主 Agent 的完成宣告

Reviewer 不能把硬失败改成通过；Reviewer 的高风险反对意见应触发 ASK 或阻止自动完成，并把任务、diff、硬证据与 Reviewer 理由交给用户裁决。最终裁决权属于用户或预先批准的组织策略。
