## 3. F1：让 DOM 附件的结果和 turn 身份真正参与判定

当前问题位置：`release/win7-product-v3/a9-win7-27-report.cjs` 的 `parseDomExport` / `validateOutcomeProjection`。该历史文件只作参考；修复实现进入新候选对应文件。

### 实施要求

- 明确新版本投影附件契约。若新增必填字段或改变语义，应版本化并新增 ADR；不得把旧 schema 的含义静默改掉。
- 查询附件提供会话和实际查询事实；DOM 附件必须保留并解析 `displayed_outcome`、`latest_persisted_turn_id`、阶段、逐行观察值。
- 从正式 snapshot 独立采集最新持久化 turn 身份，从查询导出获取终态事实，从真实 DOM 获取结果文字；不能从同一手填字段反向填充三份“证据”。
- 重启、切回和补载后的 DOM 结果/turn ID 均与各阶段适用查询及 snapshot 相符。当前测试场景必须是不同 turn 的旧失败、新 verified 成功，较新成功是最终持久化事实。
- 报告中的便利汇总字段只能由附件推导或交叉校验；不允许覆盖附件事实。附件之间的会话、run、阶段和源码/候选绑定须一致。开发机与候选实机运行身份明确分开。

### 必须拒绝的反例

报告仍声称成功时，分别只修改附件：结果改成失败、最新 turn 指向旧失败、结果字段缺失、turn 字段缺失、类型错误、阶段/会话错绑、旧新轮次共用 turn ID。修改后重新计算正确附件哈希，确保测的是语义拒绝而不是哈希不符。

验收标准：上述各项都必须被正式验证函数拒绝；与真实产品事件形态一致的正确导出通过。历史失败事件 outcome/verification 为空时，按已声明事件语义处理，不伪造原始持久化值。

## 5. F3：真实覆盖审批恢复及四项旧集成要求

kit 保留独立的 `APPROVAL-FAILURE-ORDER` 用例与投影用例，不再以替换编号移除旧要求。每个子场景必须记录实际执行和明确断言。

| 子项 | 必需场景和判定 | 不能替代它的证据 |
|---|---|---|
| 审批恢复顺序 | 通过正式审批链形成决定及恢复后的实际 `tool_start`；绑定同一 conversation/task/turn/approval/工具目标；决定 event ID 必须更早，且恢复工具事件必须存在 | 只有 model_chunk/model_note、空数组 `.every()`、另一轮次的工具事件 |
| 拒绝零目标副作用 | 单独执行拒绝场景，采集目标前后存在性、字节哈希及相关状态；目标不变且未执行被拒绝动作 | 只检查文件仍然存在 |
| 失败状态不冒充成功 | 分别覆盖非零退出、工具错误、取消、cleanup 未确认；检查持久化结果、UI 结果和相关诊断，不得被标 verified success | 用 Provider 503 代表全部失败类型，或用正常取消代表未知清理 |
| 查询失败后的可见重试 | 实际触发一次历史查询失败，显示错误和可用重试入口；通过 UI 重试成功，前后事件 ID 稳定、不重复且内容正确 | 正常重启加载成功、源码含“重试”字符串 |

安全要求：审批允许路径只作用于测试创建、已清点的临时专用目标，经真实目标绑定确认执行；不对用户仓库、真实远端或历史资产做破坏性动作。测试目标逐个绑定，不引入批量删除。

非零退出等可通过确定性 fixture 和正常产品边界构造。难以安全制造的 cleanup 未确认、查询故障，使用已有的测试替身/故障边界在隔离测试实例中执行，并明确记录注入点和证据等级；不得修改冻结源代码、暴露产品高权限测试接口、降低真实清理保证或把模拟宣称为真实 OS 故障。没有合适测试接缝时，说明最小测试侧方案及所需授权，不跳过后直接宣布完成。

必需反例：移除恢复工具事件、只留模型文字、交换审批决定与工具事件顺序、换成其他 turn 的工具事件、修改拒绝目标内容、把失败显示成成功、重试仍失败、重试重复事件。分别必须使对应断言拒绝。

## 6. F4：必须证明旧事件真的在后续分页中被加载

当前产品首次读取最近 300 条事件，Inspector 最多显示最近 60 行；执行时核实真实常量，不硬改产品阈值来方便测试。

### 场景设计

1. 在测试专用会话中通过正式产品链路形成旧 `failed · not_applicable` 轮次。
2. 形成足够多的持久化过程事件，使旧失败终态位于首次 300 条查询之外；再形成较新 `completed · verified` 轮次。优先通过确定性 Provider 多工具旅程产生真实事件，不用几百次无意义模型请求；若采用持久化夹具，单列其证据等级，不能冒充全链路生成。
3. 正常退出并重启，证明初次查询 `hasMore=true`、旧失败不在首批事件中，最新结果为成功。
4. 点击真实“加载更早记录”，记录正式查询请求的 `beforeEventId`、响应页和旧事件身份，等待加载完成。
5. 证明旧失败事件由这次或后续明确分页加入历史，并检查可见过程历史、最近 60 行及全局结果；最新 turn 与成功结果保持不变。
6. 切换会话再切回，检查隔离、去重和投影一致性。

### 重要判定规则

- 不要要求最近 60 行一定变化：补载的是旧事件，它们可能不进入 Inspector 最近 60 行。应验证实际分页与新增历史事实，再验证可见有界投影仍正确。
- 不要强制旧失败出现在最近 60 行；应在已加载历史/对应旧轮次详情及查询附件中验证其存在与身份。
- 不允许用 `FULL_HISTORY_ALREADY_LOADED`、按钮存在、等待结束、行数相同或“点过按钮”代替加载成功。
- 查询附件必须保存真实 `limit`、`beforeEventId`、`hasMore`、返回范围和成功/失败信息，不能硬编码 `has_more=false`。超过单次查询上限时按实际分页完整采集并明确合并规则。
- 无加载按钮、按钮禁用、未发请求、请求失败、返回空页、未纳入旧失败，均不能把本场景标为 PASS；正向回归因 fixture 不满足前提应失败，正式未执行项准确记 NOT_PERFORMED。

必需反例：仅声称点击但没有请求；游标未向旧事件推进；分页没有带来新事件；请求失败；旧失败仍未加载；补载后全局结果错误回退；旧事件被重复合并。通过同一 driver/报告判定拒绝。
