## 3. 待裁决问题

### Q1 预演用什么授权文件

问题：p02 完整性阶段每次都要求一个 `WIN7_43_RELEASE_AUTHORITY` 文件，状态为 `APPROVED_FOR_WIN7_43_VALIDATION`，并绑定 run-id、目标账户和候选哈希（见[套件说明](../../release/win7-product-v3/A9_BATCH2_WIN7_VALIDATION.md)）。关口 A 在冻结后才签，预演时没有正式授权文件。这是任务书与套件之间的矛盾，需要裁决。

| 选项 | 影响 |
|---|---|
| A：为每次预演单独签一份预演授权文件 | 走与正式相同的代码路径，预演保真度最高。文件绑定预演专用 run-id 和当次包哈希，不能当作关口 A。需要负责人对每份文件的 SHA-256 回复同意 |
| B：修改完整性脚本，让预演在无授权时降级 | 预演不再覆盖授权校验路径，该路径第一次真实运行推迟到正式执行。须改 `a9-batch2-package-integrity.cjs`（在 §6.1 路径内），再做一轮开发机验证 |

推荐 A：授权校验是套件最容易出错的路径，应在预演里先跑一遍。预演授权文件的命名和 run-id 登记都与正式文件分开。

### Q2 运行预算

问题：两次连续成功预演前，驱动首次在真实 Electron 和 PowerShell 上运行，出现需要修复的缺陷的可能性不能排除。预算要在“逐次批准”和“一次批准”之间选。

| 选项 | 上限 | 影响 |
|---|---|---|
| A：逐次批准 | 每次运行单独批准，每次 ≤16 请求、≤7200 秒 | 控制最强。每次失败都多一次往返，最短也要 3 次批准 |
| B：有限滚动批准 | 预演最多 4 次（含失败），总计 ≤64 请求、≤8 小时；同一失败连续两次即暂停诊断（[§6.4](../tasks/A9_33_BATCH_2_WIN7_ACCEPTANCE.md#64-停止诊断与核号)）；首次预演结束后先向负责人报告再继续；每个新包哈希传输前报备；修复只能在 §6.1 路径内 | 往返最少。远端动作闭集和上限固定，超出即停 |
| C：只批首次预演 | 1 次，≤16 请求、≤7200 秒 | 先取得首次真实观察，再决定后续。后续每步另批 |

推荐 B：首次预演后有强制报告点，上限由数字固定，且不放宽 §6.4。正式执行不在本预算内，须关口 A 后另批。
时间窗建议：自负责人回复日起 3 个日历日；每次运行 ≤7200 秒。

## 4. 远端动作闭集

下表之外的动作均不在授权内。

| 步骤 | 动作 | 性质 |
|---|---|---|
| R1 | 经 SSH 只读预检：`ver`、`query user`、进程表、磁盘空间、已有目录是否存在 | 只读 |
| R2 | 创建新根下的 `deploy`、`work`、`data`、`evidence` | 写，仅新根 |
| R3 | 传输 ZIP、授权文件、输入锁、构建套件登记、阶段请求文件；两端各算 SHA-256 | 写，仅新根 |
| R4 | 在 `deploy` 解压并校验 | 写，仅新根 |
| R5 | 注册、回读、运行、移除一次性计划任务 | 写，任务逐项移除 |
| R6 | 运行 p01～p10（G0～G4） | 写，仅新根 |
| R7 | 取回全部 `evidence`，逐文件复算字节数与哈希，本机做秘密扫描 | 读 |
| R8 | 记录后飞行进程表；残留先留证，不先强杀 | 读 |

不在授权内：安装或升级软件、改系统与安全设置（防火墙、UAC、DPI、自动登录、账户）、触碰任何旧根、联网下载、使用真实 Provider、推送或合并、使用 Win10、重复使用旧预算或已消费授权、恢复 ENGINEERING_02 的 p17/w16。

## 5. 停止条件

停止条件沿用 [A9-33 §6.4](../tasks/A9_33_BATCH_2_WIN7_ACCEPTANCE.md#64-停止诊断与核号)，不放宽。补充三条：

1. 目标机器名、账户 SID、完整性等级或会话与批准值不符：立即停止，不进入 R2。
2. 任一哈希两端不一致：停止下游，保存两端原始输出。
3. 到达时间窗或请求上限：停止接单，不自动续预算。

预演失败不计入“连续两次成功”，连续计数归零。失败的原始证据保留，不覆盖。
