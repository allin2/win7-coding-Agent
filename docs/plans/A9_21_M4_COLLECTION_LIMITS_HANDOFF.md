## 1. 背景

- 渲染端 `a9-workbench.js` 的 `state.inspectorEvents`（Map，eventId → 事件）与 `state.turnEvents`（Map，turnId → `{ ids, events }`）
  没有上限（`ingestEvents`，约第 270 行）：实时轮询与“加载更早记录”带来的事件只增不减，每个事件还在对话流里保留一个 DOM 节点。
  工具时间线只显示最后 60 条（`renderTimeline`），但数据本身不受限。
- Main 进程 `main.js` 的 `runtimeState.blockedRequests` 保存每一个被拦截请求的完整 URL（第 1171 行 `onRequestBlocked`），没有上限；
  这些 URL 只在诊断里以数量出现（第 220 行 `blocked_request_count`）。
- 演示中发现一个必须处理的问题：快照轮询会重复带回刚被淘汰的事件，若照常接收，会反复“收回—淘汰”，释放计数虚高
  （演示中 120 个事件报告释放 542 条）。§3 W-4 规定了处理方式。

A9-18 工作树（`/Users/qlyf/Developer/win7-coding-agent-memory-optimization`）有一版实现，只作参考，不得整文件复制或 cherry-pick。
它的淘汰按 Map 插入顺序而不是 eventId，会把用户刚加载的更早记录立即挤掉；`blockedRequests` 每次写入都对整个数组求和，也不要沿用。

## 3. 实现要求

### 渲染端事件上限（`a9-workbench.js`）

- **W-1 上限常量**：全局 `inspectorEvents` 最多 2000 条且估算字节不超过 4 MiB；单个轮次桶最多 500 条。事件字节在首次接收时估算一次
  （如按 `JSON.stringify(event.data)` 的长度乘 2 再加固定开销）并记在事件上，淘汰时按同一数值扣减，不得每次重算。
- **W-2 淘汰规则**：超过任一上限时按 eventId 从小到大淘汰。一次淘汰到上限的 90% 再停止，避免每来一个事件就淘汰一次、重建一次对话块。
  被淘汰的事件必须同时从 `inspectorEvents`、所属轮次桶（`events` 与 `ids`）和对话流中对应的 DOM 节点里移除，不留引用。
  轮次桶的事件全部被淘汰后，桶只保留计数，不保留事件。
- **W-3 “加载更早记录”到上限即停**：`loadConversationEvents(true)` 请求的 `limit` 取 `min(300, 2000 - 当前条数)`；没有余量时不发请求。
  主动加载的更早记录不得挤掉较新的记录。之后实时事件到达时仍按 W-2 淘汰最旧的（可能正是刚加载的更早记录），这是确认过的行为。
- **W-4 不收回已淘汰的事件**：记录已淘汰事件中最大的 eventId；此后轮询快照或普通加载带回的、eventId 不大于它且不在当前集合里的事件
  一律忽略。只有用户主动“加载更早记录”带回的事件可以重新放回，并相应减少“已释放”计数。
- **W-5 计数与提示**（文案按演示确认）：
  - “已释放”计数表示当前已知但不在界面内存里的条数，重复淘汰同一事件不重复计数。
  - 对话流顶部：有释放时显示 `为控制内存，界面已释放最早的 N 条过程记录（本地记录完整保存）。`；达到全局上限时追加
    ` 已达界面上限 2000 条，更早记录不再加载。` 且不显示“加载更早记录”按钮；未达上限时保持现有的“还有更早的过程记录 / 加载更早记录”。
  - 轮次块顶部：该轮有释放时显示 `本轮较早的 N 条过程已从界面释放，下方只显示最近 M 条。`
  - 加载失败时保持现有的错误文案与“重试加载”按钮。
- **W-6 重置**：切换或新建对话（`resetConversationEvents`）时清零所有计数、字节与已淘汰标记。
- **W-7 行为不变**：A9-19 的实时过程（运行中工具项、流式预览、已运行时长、分组）与工具时间线“最后 60 条”的显示规则保持不变；
  `renderConversation` 的签名要包含释放计数与是否达上限，保证提示随之刷新。

### Main 进程被拦截请求（`main.js`）

- **M-1**：`blockedRequests` 最多保留 500 条、合计不超过 1 MiB（按字符串长度乘 2 计），单条 URL 先截到 2048 个字符；超出时淘汰最旧的。
  字节合计增量维护，不得每次写入都遍历整个数组。
- **M-2**：诊断里 `blocked_request_count` 保持原义，表示启动以来被拦截的请求总数（含已淘汰的）；另加 `blocked_request_dropped`
  表示因上限淘汰的条数。
- **M-3**：把记录逻辑写成 `main.js` 内的一个独立函数（例如 `recordBlockedRequest(url)`），用明确的开始/结束注释包住，
  以便测试从源码中取出该函数在 `vm` 中执行（`main.js` 被加载时会启动 Electron，不能直接 require）。

## 5. 测试要求（`src/shell/tests/product/**`）

但不得改变产品常量的默认值）：
1. 实时事件超过全局上限：集合大小回到上限的 90% 以内，留下的是 eventId 最大的一批；被淘汰事件不在 `inspectorEvents`、轮次桶和对话流 DOM 中。
2. 单个轮次超过 500 条：该轮只保留最新的，轮次块显示正确的释放数量与剩余数量。
3. 字节上限：少量大事件先触发字节上限，按字节淘汰。
4. **轮询重复带回**：同一批已淘汰事件经多次快照轮询重复送达，集合不变，释放计数不增加（演示中的 542 问题）。
5. 主动加载更早记录：有余量时按余量请求并放回，释放计数相应减少；无余量时不发请求并显示上限提示；不会挤掉较新的记录。
6. 切换对话后计数与标记清零。
7. A9-19 实时过程用例（`a9-19-live-progress.test.ts`）与工作台合同用例全部继续通过。

9. 一条超长 URL 被截到 2048 个字符；字节上限先于条数触发时按字节淘汰。
10. 源码约束：诊断计数字段存在；`onRequestBlocked` 调用该记录函数；`deniedPermissions` 相关代码与基线一致。
